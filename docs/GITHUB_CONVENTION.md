# 백엔드 GitHub 협업 규칙

이 문서는 Osori 백엔드 저장소에서 함께 작업할 때 따르는 규칙입니다. 프론트엔드는 별도의 저장소에서 관리합니다.

## 브랜치 전략

- `main`은 백엔드 팀원들의 작업을 통합하는 브랜치입니다. `main`에서 직접 개발하거나 Push하지 않습니다.
- 작업을 시작할 때 최신 `main`에서 작업 브랜치를 만듭니다.
- 한 브랜치에는 하나의 기능이나 명확한 수정 단위를 담습니다.
- 작업이 끝나면 `main`을 대상으로 PR을 생성합니다. 리뷰와 충돌 여부를 확인한 뒤 Merge합니다.

## 브랜치 이름

`종류/작업명` 형식을 사용하고, 소문자와 하이픈으로 작성합니다. 백엔드 전용 저장소이므로 이름에 `backend`를 넣을 필요는 없습니다. 이슈를 사용하는 경우 `feat/12-login-api`처럼 번호를 포함할 수 있습니다.

```text
feat/login-api
feat/user-profile
fix/login-error
docs/api-guide
```

## 커밋 메시지

`type: 작업 내용` 형식의 한 줄로 작성합니다. 작업 내용은 한국어로 쓰고, 관련 파일끼리 묶어 가능한 작은 작업 단위로 나눕니다. 공동 작성자(Co-authored-by) 표시는 추가하지 않습니다.

| Type | 용도 | 예시 |
| --- | --- | --- |
| `feat` | 기능 추가 | `feat: 로그인 API 추가` |
| `fix` | 버그 수정 | `fix: 로그인 오류 수정` |
| `refactor` | 동작 변경 없는 구조 개선 | `refactor: 사용자 조회 로직 분리` |
| `docs` | 문서 작성·수정 | `docs: API 실행 방법 추가` |
| `test` | 테스트 추가·수정 | `test: 로그인 API 테스트 추가` |
| `chore` | 설정·의존성·기타 작업 | `chore: 의존성 추가` |

## PR 규칙

- PR 대상 브랜치는 `main`입니다.
- 제목은 담당 영역 Prefix로 시작합니다. 이 저장소에서는 `[BE]`를 사용합니다.
- 예: `[BE] 로그인 API 구현`
- 본문에는 주요 변경 사항과 테스트 결과를 간단하게 작성합니다. 테스트하지 못했다면 그 이유를 적습니다.
- API 요청·응답 형식이나 환경 변수가 바뀌면 관련 팀원에게 공유합니다. 프론트엔드에 영향을 주는 변경은 프론트엔드 팀원에게도 알려줍니다.

## 작업 순서 예시

```bash
# main으로 이동하고 최신 변경 사항을 받습니다.
git switch main
git pull origin main

# 작업 브랜치를 만듭니다.
git switch -c feat/login-api

# 작업 후 변경 사항을 확인하고 커밋합니다.
git status
git add <변경한 파일>
git commit -m "feat: 로그인 API 추가"

# 작업 브랜치를 원격 저장소에 올립니다.
git push -u origin feat/login-api
```

GitHub에서 `feat/login-api`를 `main`으로 합치는 PR을 생성합니다. 변경 사항과 테스트 결과를 작성하고, 리뷰와 충돌 확인을 마친 뒤 Merge합니다.
